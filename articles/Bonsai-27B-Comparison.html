Tool Calling: The Real Gap

💥 1-bit — Tool Calling: 66 / 100

  • 17.5% degradation from FP16 baseline — the single largest loss of any capability
  • Degrades 4.6× more than math (3.8% loss)
  • Function call format drift becomes frequent: wrong parameter names, hallucinated args, malformed JSON
  • MCP reliability questionable for multi-step agentic chains
  • Best for: chat, summarization, text gen where exact tool calls aren't critical

🧊 Ternary — Tool Calling: 74 / 100

  • 7.5% degradation from FP16 baseline — usable, noticeable but not broken
  • ✅ PrismML explicitly demos MCP integration with this variant (Demo II, M5 Max)
  • ✅ Demos Hermes agentic workflow end-to-end (Demo I, RTX 5090)
  • Occasional tool call failures under load, but generally reliable for agent loops
  • Their recommended operating point for agentic/MCP work

Verdict for MCP / Tool Use on 16 GB

🎯 The Recommendation

Ternary (~8 GB) is the only viable choice for agentic/MCP work. 74/100 on tool calling is degraded but workable — it's what PrismML themselves demo with Hermes and MCP. Fits your 16 GB card with ~7.6 GB to spare at 4K context.

1-bit (~2.9 GB) at 66/100 tool calling will produce frustrating failures in agentic loops — wrong function calls, malformed JSON, dropped tools. The 10 GB of free VRAM is tempting, but the capability gap in exactly the area you care about is too wide. This variant is a chat/summarization model in practice, not an agent model.

Note: Both need Prism ML's custom llama.cpp fork — stock Ollama/llama.cpp won't load them. No idea when Ollama support ships.
