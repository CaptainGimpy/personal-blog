1. Hermes Memory System Architecture

Hermes Agent uses a tiered memory architecture with four layers that work together. Understanding these tiers is essential before designing an Obsidian-based memory skill.

┌─────────────────────────────────────────────────────────────────┐ │ HERMES MEMORY ARCHITECTURE │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ LAYER 1 — BUILT-IN MEMORY (Hot) │ │ │ │ MEMORY.md (2,200 chars) + USER.md (1,375 chars) │ │ │ │ Frozen snapshot at session start → injected into prompt │ │ │ │ Agent manages via `memory` tool (add/replace/remove) │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ LAYER 2 — SESSION SEARCH (Warm) │ │ │ │ SQLite + FTS5 — all sessions, unlimited, ~20ms queries │ │ │ │ `session_search` tool: discovery / scroll / browse │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ LAYER 3 — EXTERNAL MEMORY PROVIDERS (Cold) │ │ │ │ 8 plugins: Honcho, OpenViking, Mem0, Hindsight, │ │ │ │ Holographic, RetainDB, ByteRover, Supermemory, Memori │ │ │ │ One active at a time; runs ALONGSIDE built-in memory │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ LAYER 4 — OBSIDIAN / WIKI (Long-Term Archival) │ │ │ │ Markdown knowledge base — human-reviewable, git-backed │ │ │ │ Accessed via Obsidian skill, file tools, or MCP server │ │ │ └─────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────┘

1.1 Built-in Memory (The Hot Tier)

StorePurposeChar LimitTypical Entries
MEMORY.mdAgent's personal notes — environment facts, conventions, lessons2,2008–15
USER.mdUser profile — preferences, style, identity1,3755–10

Key behavior: Memory is a frozen snapshot captured once at session start and injected into the system prompt. Changes during a session persist to disk but don't appear in the prompt until the next session. This preserves LLM prefix caching.

The memory tool supports: add, replace (substring match via old_text), remove (substring match). When full, the agent reads current entries and consolidates before retrying.

⚠ Capacity Constraint
Combined ~3,575 chars (~1,300 tokens). This is not a knowledge base — it's the agent's working identity. Stable, verbose knowledge belongs in Layers 3 or 4.

1.2 Session Search (The Warm Tier)

All CLI and messaging sessions are stored in ~/.hermes/state.db with FTS5 full-text search. Three calling shapes:

  • Discovery — session_search(query="auth refactor") returns top sessions with FTS5-matched snippets + bookend messages (goal + resolution)
  • Scroll — session_search(session_id="...", around_message_id=N) browses within a session
  • Browse — session_search() lists recent sessions chronologically

Zero LLM cost — pure SQLite FTS5. Always available across sessions. This is free, always-on memory that doesn't count against the memory budget.

1.3 External Memory Providers (The Cold Tier)

Hermes ships with 8 external providers. Only one can be active at a time, and it runs alongside built-in memory (never replaces it).

ProviderStorageCostUnique Feature
HonchoCloud / Self-hostedPaid / FreeDialectic user modeling + session-scoped context injection
OpenVikingSelf-hostedFreeFilesystem hierarchy + tiered retrieval (ByteDance/Volcengine)
Mem0Cloud / Self-hostedFree / PaidServer-side LLM extraction + self-hosted mode
HindsightCloud / LocalFree / PaidKnowledge graph + reflect synthesis
HolographicLocalFreeHRR algebra + trust scoring — zero deps
SupermemoryCloud / Self-hostedFree / PaidContext fencing + session graph ingest
MemoriCloudFree / PaidTool-aware memory + structured recall

When active, the provider automatically: injects context into system prompt, prefetches relevant memories before each turn, syncs conversation turns, extracts memories on session end, and mirrors built-in memory writes.

1.4 Self-Improvement Loop

Hermes has a built-in closed learning loop that runs in the background:

TriggerAction
After 10 user turnsMemory review agent updates USER.md and MEMORY.md
After 15 tool iterationsSkill review agent updates or creates skills
Nightly (4 AM on stale sessions)Final pass on untouched sessions — captures learnings before context expires

The review agent gets the transcript, reads it, and decides: "anything worth saving?" If so, it writes. If nothing stands out: "Nothing to save." and stops. The main chat never sees this background agent.

2. The Observability Problem

The central challenge this research addresses: Hermes' built-in memory is invisible to the user. You can't open MEMORY.md in a nice UI, graph the connections, or cross-reference it with your own notes. Obsidian fills this gap by providing:

  • Visualization — Graph View shows memory connections via wikilinks
  • Reviewability — Open any note and edit it directly
  • Durability — Git backup, iCloud sync, no proprietary format
  • Cross-agent portability — Claude Code, Codex, and Hermes can all share the same vault

3. Obsidian Integration — The Four Layers

Based on community patterns, official docs, and GitHub discussions, there are four approaches to integrate an Obsidian vault with Hermes, each with different complexity/power trade-offs:

3.1 Layer 0: Filesystem-First Obsidian Skill (Built-in)

What it is: The bundled obsidian skill reads/writes Markdown files in the vault directory via standard file tools (read_file, write_file, search_files, patch). No app required — Hermes works headlessly.

Configuration
# In ~/.hermes/.env:
OBSIDIAN_VAULT_PATH="G:\My Drive\Vault\MindEmporium"

Capabilities:

  • Read any note via read_file
  • Search notes via search_files (content regex or filename glob)
  • Create/append/edit notes via write_file / patch
  • Create wikilinked notes: [[Note Name]] syntax

Limitations: No semantic search, no RAG — pure regex/filename matching. For small-to-medium vaults this is often sufficient because the agent can reason about what to search for.

3.2 Layer 1: Scoped Vault Folder Sync (Recommended Starting Pattern)

What it is: Create a dedicated subfolder in your vault (e.g., /Agent Memory or /Hermes) that Hermes reads/writes. This keeps agent-generated content separate from your personal notes.

Official recommendation from hermes-agent.ai:

  • Start with a scoped /Hermes or /Agent Memory folder
  • Decide what Hermes may write first: durable project facts, session summaries, skills, daily notes
  • Keep credentials, client secrets, and private journals outside the scoped folder
  • Run one smoke test: ask Hermes to save a durable fact, then verify it appears in Obsidian
  • Review first generated notes before expanding access
✅ Key Insight — Symlinking for Review
Obsidian users can symlink their memory and skill files into the vault to see and review what the self-improvement loop is writing. This gives you Obsidian's graph view and editing capabilities over Hermes' own runtime files without moving them out of ~/.hermes/memories/.

3.3 Layer 2: MCP Server for Vault Operations (Most Powerful Seam)

What it is: Expose vault operations (search, read, save, daily notes, world summaries) as an MCP (Model Context Protocol) server. Hermes connects via discover_mcp_tools(). Zero Hermes-specific code — the same MCP server works in Claude Code, Claude Desktop, Cursor, etc.

This approach was the recommended solution in the obsidian-second-brain GitHub issue #60 by the project maintainer:

┌─────────────────────────────────────────────────────────────────┐ │ MCP-BASED VAULT ACCESS │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ Hermes Agent ──→ discover_mcp_tools() ──→ MCP Server │ │ │ │ │ Tools exposed: │ │ │ • obsidian_search(query) ← searches vault │ │ │ • obsidian_read_note(path) ← reads a note │ │ │ • obsidian_save_note(path,content) ← writes note │ │ │ │ │ │ Same server also works in: │ │ │ Claude Code │ Claude Desktop │ Cursor │ │ └─────────────────────────────────────────────────────────────────┘

Setup (from obsidian-second-brain repo, obsidian-mcp-server branch):

git clone https://github.com/eugeniughelbur/obsidian-second-brain
cd obsidian-second-brain
git checkout obsidian-mcp-server
export OBSIDIAN_VAULT_PATH="G:\My Drive\Vault\MindEmporium"

# Test (no Hermes needed):
uv run --with mcp python integrations/obsidian-mcp-server/live_test.py "some query"

# Then configure Hermes MCP to point at:
# Command: uv run --with mcp python /abs/path/integrations/obsidian-mcp-server/server.py
# Environment: OBSIDIAN_VAULT_PATH=...

3.3 Layer 3: Vector Store + Nightly Ingestion (Advanced)

What it is: Mart Kempenaar's iCloud-native setup. A Weaviate vector store is populated nightly by a Hermes-managed cron job that ingests new/modified/deleted notes. This enables semantic similarity search across a large vault.

# Nightly cron workflow (Hermes-managed):
1. Cron fires at 2 AM
2. Script scans vault for new/modified/deleted notes (git diff)
3. Content + metadata (creation date, vault, folder, tags) → Weaviate
4. Hybrid search: meaning-based similarity + concrete filters (folder/tag)
5. Recent notes get a boost factor
6. LLM distills important changes → long-term memory entries in vault

Trade-off: Highest power but requires running a vector DB instance. Overkill unless the vault is very large (500+ notes) or semantic search is critical.

4. Skill System & Dynamic Knowledge Retrieval

4.1 How Skills Load

Skills are the agent's procedural memory. At session start:

  1. All active skill descriptions (first ~57 chars) are injected into the system prompt as the available skill index
  2. When a skill matches the task, the agent calls skill_view(name) to load the full SKILL.md content + linked files
  3. The skill body contains instructions, commands, and workflows the agent follows
  4. Skills are cached — repeated skill_view() calls on the same skill return instantly
⚠ Key Constraint
Having too many active skills simultaneously loads all their descriptions into context, which can confuse the model. Keep only the skills you actively use. The agent does not automatically discover which skill to load — the description must be clear and unique enough for the model to choose it.

4.2 The Self-Improvement Skill Creation Loop

Hermes creates skills automatically when:

  • A complex task is completed successfully (5+ tool calls)
  • An error is hit and recovered from
  • A user correction reveals a better approach
  • A non-trivial workflow is discovered

Skills are also cached and managed — the Curator (background maintenance system) tracks usage via ~/.hermes/skills/.usage.json (use_count, view_count, patch_count, last_activity_at, state, pinned). Stale skills are auto-archived.

4.3 Project Context Files

These files provide project-level instructions auto-injected into the system prompt based on working directory:

FileScopeUse Case
.hermes.mdRoot + subtree (walks to git root)Hermes-specific rules that inherit from parent dirs
AGENTS.mdCwd onlyPortable agent instructions (Hermes, Claude Code, Codex)
SOUL.md$HERMES_HOME (always loaded)Agent identity — not project rules

For vault-backed memory: Placing an AGENTS.md in the vault root with directives like "always search my vault before answering" can encode the desired retrieval behavior without a custom skill.

5. Community Patterns & Case Studies

Case Study 1: Artem Zhutov — Self-Learning User Profile

Artem ran Hermes across Discord channels and observed it:

  • Wrote 7 entries into USER.md entirely on its own (without being asked)
  • Auto-created a skill after a YouTube → NotebookLM research workflow
  • Created an obsidian-evening-routine-capture skill from a nightly review pattern
  • Uses Discord channel-specific skills per area (coding, content, vault interaction)

Key takeaway: The self-improvement loop works. The agent learns from you even when you don't explicitly teach it.

Case Study 2: Mart Kempenaar — iCloud-Native Agent

Mac mini running Hermes 24/7 with:

  • iCloud synced Obsidian vault (keep-downloaded flag to prevent macOS eviction)
  • Weaviate vector store for semantic search over multi-vault knowledge
  • Nightly cron: git diff → LLM distillation → long-term memory in vault
  • Calendar + Reminders integration via ical-guy
  • Morning brief with relevant project notes pre-fetched
  • PII redaction in the LLM pipeline before passing any data

Key takeaway: Full automation requires running Hermes on a persistent machine (Mac mini, server). The nightly "dreaming" cycle (distilling activity into long-term memory) is a powerful pattern.

Case Study 3: savez + eugeniughelbur — MCP Vault Server

GitHub issue #60 on obsidian-second-brain repo. The maintainer built an MCP server exposing vault operations as tools. Clear boundary established:

  • Hermes agent memory (how it behaves, tricks it learns) → left untouched
  • Obsidian as second brain (what you read, ideas across MD files) → MCP tools
  • The two stay distinct — the agent uses MCP to query/add to knowledge, not to overwrite its own behavior memory

Key takeaway: The MCP approach is architecturally cleanest — same server works across all MCP-compatible agents. Build once, use everywhere.

6. Recommended Architecture: The Expedient Path

Based on this research, the most expedient path to use an Obsidian vault as Hermes' memory/knowledge store involves three tiers working together, starting simple and scaling as needed:

7. Skill Specification: Vault Knowledge Retrieval

Here is the recommended structure for a custom skill that ensures Hermes pulls the most relevant skill data, user preferences, and session data from the Obsidian vault on every session start:

---
name: vault-knowledge-retrieval
description: "Use when answering questions or starting work: search the Obsidian vault for relevant context before responding. Always load this skill at session start if OBSIDIAN_VAULT_PATH is set."
version: 1.0.0
platforms: [windows, linux, macos]
---

# Vault Knowledge Retrieval

## When This Skill Activates

- **Auto-activate:** At the START of every session when OBSIDIAN_VAULT_PATH is configured
- **On user query:** When the user asks a question that might reference prior work, project notes, or personal knowledge
- **On task start:** Before beginning any complex or project-related task

## Vault Location

Resolved from `OBSIDIAN_VAULT_PATH` env var (set in `~/.hermes/.env`).

## Session-Start Protocol (RUN THIS EVERY SESSION)

### Step 1: Orient in the vault

Read the vault index / MOC (Map of Content) first:

```python
from hermes_tools import search_files, read_file

vault = os.environ.get("OBSIDIAN_VAULT_PATH", "")
if not vault:
    return  # No vault configured — skip

# Check for AGENTS.md directives
agents = os.path.join(vault, "AGENTS.md")
if os.path.exists(agents):
    read_file(agents)  # Load project context rules

# Read MOC if it exists
moc_paths = search_files(pattern="MOC.md OR Index.md", target="files", path=vault)
for p in moc_paths["matches"][:1]:
    read_file(p["path"])  # Understand vault structure
```

### Step 2: Search for relevant context

Before answering a question or starting a task:

1. Extract key terms from the user's query
2. Search the vault for those terms:
   ```
   search_files(pattern="", path="$OBSIDIAN_VAULT_PATH", file_glob="*.md", target="content", limit=10)
   ```
3. Read the top 2-3 most relevant matching notes
4. Synthesize findings into the response, citing specific note paths

### Step 3: Check for related session history

```
session_search(query="", limit=3, sort="newest")
```

This catches relevant prior discussions even if they aren't yet reflected in the vault.

## Write Protocol

When storing new information to the vault:

1. Place notes in the appropriate subfolder (Projects, Areas, Resources)
2. Use `[[wikilinks]]` to cross-reference related notes
3. Prefix agent-written notes with metadata block:
   ```
   **Source:** Hermes Agent
   **Date:** YYYY-MM-DD
   **Session:** @session:/
   ```
4. Update the MOC or index if creating a new major topic note

## Folder Conventions

```
Agent Memory/
├── index.md           # Agent's MOC — updated on every write
├── session-summaries/ # One note per significant session
├── project-facts/     # Durable project config, conventions, blockers
└── learned-skills/    # Skill documentation vault copy (review surface)
```

## Performance Notes

- `search_files` (ripgrep-backed) is ~50ms per query — fast enough for interactive use
- Session search (FTS5) is ~20ms per query — effectively free
- Only load full note content with `read_file` when the search snippet is relevant
- For very large vaults (500+ notes), consider the MCP server approach with semantic search

8. Pitfalls & Caveats

⚠ Don't Replace Hermes Memory With Obsidian

Hermes' built-in memory (MEMORY.md/USER.md) handles the agent's behavioral identity — preferences, corrections, environment facts. Obsidian holds long-form knowledge — research notes, project docs, reference material. They serve different purposes. Hermes needs both.

⚠ Security — Vault Scope

Do not give Hermes full vault access on day one. Start with a scoped /Agent Memory folder. Your vault likely contains credentials, client data, personal journals, and API keys. The vault is accessed via file tools — Hermes can read anything in the exposed path.

⚠ Skill Overload

Having too many active skills loads all descriptions into the system prompt. The model can get confused about which skill applies (e.g., activating PowerPoint instead of Obsidian for a note-taking task). Keep only the skills you actively use and give them clear, non-overlapping descriptions.

⚠ Cross-Profile Memory Isolation

Don't point two Hermes profiles at the same memory directory. Memory writes are automatic — two writers sharing one home will compound entries into state neither agent authored. Use external memory providers (Honcho, etc.) for shared context across profiles.

⚠ Frozen Snapshot Pattern

Memory changes during a session are persisted to disk immediately but don't appear in the system prompt until the next session. If you correct something in the vault mid-session, the agent won't see it until the next session start. This is by design — it preserves prompt caching.

⚠ The MCP Path Isn't Fully Baked

The obsidian-second-brain MCP server is on a feature branch and has been tested with a standalone MCP client but not yet driven by Hermes itself. The architecture is sound (MCP is Hermes-native), but you'll be on the bleeding edge if you go this route.
